Agent Compatibility Operator Runbook

Operating Sequence

  1. Discover available Codex and ChatGPT surfaces as metadata only.
  2. Register stable identities and compare discovered versions with approved project memory.
  3. Qualify each agent for the exact operation, schema, authority, privacy, cost, latency, and supervision requirement.
  4. Select deterministically from qualified candidates and preserve an explainable fallback chain.
  5. Invoke callable surfaces with durable idempotent receipts, or create a supervised handoff with bounded context and resume instructions.
  6. Validate, redact, and admit output with provenance. Continue independent slices when one agent or credential is unavailable.

Callable Versus Handoff

ConditionOperator action
Codex or ChatGPT surface is callable and authorizedInvoke through its adapter; bind qualification, selection, input hash, version, and correlation IDs to the receipt.
Agent exists but only conversation is availableCreate a chronological supervision request containing bounded context and exact product-specific resume instructions. Status remains waiting, not succeeded.
Surface should be available but is notNotify the user and block only dependent work. Continue independent and enabling slices.
Useful surface does not existRecord a future opportunity; do not block the run.
Outcome is unknown after an external startDo not retry blindly. Reconcile with the provider or route the exact invocation to supervision.

Registering Public and Private Agents

For every agent, record stable ID, product, visibility, publisher, portable source URI, discovered version, integrity and trust status, and declared surfaces. Public fallback is permitted only when project policy allows it and the fallback independently qualifies. A personalized private agent may be preferred in project memory.

Do not customize installed private-agent files from a project run. Store project preferences, prompts supplied by the project, assumptions, and output-handling rules in project memory. Plugin development is a separate, explicitly authorized activity.

Adding an Adapter

  1. Add a provider-neutral discovery mapper and reject credentials in metadata.
  2. Declare each surface kind, operation, schema, and execution mode.
  3. Add qualification mapping for authority, auth-reference availability, data residency, retention, telemetry, cost, latency, supervision, reversibility, replayability, and PHI eligibility.
  4. Add lifecycle receipt handling and idempotency for callable operations.
  5. Add handoff construction and exact-invocation supervision gates.
  6. Add bounded context packaging and output admission.
  7. Add deterministic fake adapter tests for normal operation, outage, expired authorization, schema drift, duplicate response, timeout, uncertain outcome, and restart.

Troubleshooting

Identity collision or spoofingReject registration. Compare stable identity, publisher, source URI, integrity evidence, and prior registry history.
Version driftDo not silently upgrade. Record drift and require an explicit project approval or configured upgrade decision; preserve rollback history.
Unauthorized callable surfaceDowngrade to handoff only when handoff is allowed; otherwise reject with qualification reasons.
Missing credential referenceBlock the dependent invocation only. Report the reference name, never the value.
Schema driftReject output admission, preserve redacted hashed evidence, and requalify the discovered surface.
Duplicate reply or restartResolve by invocation identity and durable receipt. Apply an external effect no more than once.
Prompt injection in contextQuarantine the source and exclude it from the context bundle until reviewed.
PHI or secret detectedDeny transmission and admission; retain hash-only violation evidence. Continue non-sensitive work.
Computer/browser control neededCreate mandatory supervision for the exact action. User absence does not confer authorization.
