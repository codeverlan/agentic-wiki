Mandatory PHI Intake And Behavior

The plugin must ask: Will the application being developed create, receive, maintain, transmit, display, or otherwise handle PHI? The answer is recorded as yes, no, or unknown in the intent packet, authority ledger, memory profile, and incident-log profile.

AnswerRequired behavior
YesUse synthetic or verified deidentified development data only. Keep screenshots, references, fixtures, prompts, logs, examples, and generated documentation free of real PHI. Use the HIPAA-aware metadata-only incident log and prohibit remote PHI processing.
NoUse the standard project privacy, credential, and metadata-only incident rules.
UnknownUse precautionary synthetic-only behavior and place the question in the supervision queue without blocking unrelated synthetic development.

This supports privacy-conscious development and does not claim legal certification or replace project-specific compliance review.

Design Memory Capability

Design memory is a reusable plugin capability whose content remains project-local. It preserves design principles, tokens, component patterns, user flows, screen references, responsive states, accessibility requirements, visual validation evidence, intentional exceptions, variances, and supersessions.

Memory typeRole
Design principleAccepted or proposed visual, interaction, responsive, accessibility, and brand guidance.
Component patternApproved component variants, states, tokens, behavior, and implementation references.
Screen referenceHashed screenshot or mockup with route, feature, role, viewport, application state, revision, source, PHI status, and provenance.
Visual validation resultEvidence-backed comparison between current implementation and accepted references.
Design varianceMaterial deviation, rationale, affected screens and components, authority need, and proposed disposition.

Before frontend work, agents receive bounded design context. After material frontend work, they capture synthetic visual evidence at required states and viewports, compare it with approved references, and record either validation or a design variance. Historical images remain immutable and are superseded rather than deleted.

Users can add, browse, query, approve, correct, supersede, compare, and mark intentional exceptions. Image generation, design skills, browser capture, Playwright, visual-regression tooling, and Figma remain optional external adapters.

Objective And Architecture

The two-hour objective is a complete vertical spine, not the full future runtime. A development event must become immutable evidence, produce a controlled memory proposal, affect context and impact analysis, appear as a draft wiki update, and be consumable by the plugin.

Project event -> memory observation -> immutable source -> typed memory delta -> draft wiki update -> policy and impact evaluation -> bounded context package -> coordinator disposition -> promotion or supervision -> updated planning and worker assignment

Agentic Wiki remains deterministic and inspectable. The plugin supplies coordination and reasoning. Workers submit memory delta packets; only the coordinator writes shared memory and disposes drafts.

  • Define lifecycle, provenance, authority, relationships, and prohibited-value rules for all six contracts.

  • Defer MCP, dashboards, background daemons, remote models, and Cloudflare.

Phase 1: Event-To-Draft Vertical Slice

  • Add the focused agentic-memory implementation and tests.
  • Register event packets as immutable sources and create semantic HTML drafts, claims, links, and event records.
  • Prove idempotence, supersession, and PHI, secret, credential, and hidden-reasoning exclusion.

Phase 2: Context, Impact, And Design Memory

  • Generate bounded context packages from active typed records and explicit relationships.
  • Exclude superseded records by default and surface stale or contradictory active records.
  • Report affected work and proposed follow-ups without directly changing the active queue.
  • Compile design principles, tokens, components, flows, responsive states, accessibility requirements, and approved screen references for frontend slices.
  • Store hashed synthetic screenshots and mockups as immutable sources; record material differences as design variances.

Phase 3: Public Integration Surface

  • Expose observe, propose, context, impact, disposition, and checkpoint through Python and CLI JSON contracts.
  • Keep AgenticWikiWorkspace canonical and MemwikiWorkspace compatible.
  • Advertise mutation and PHI rules in the generated capability manifest.

Phase 4: Plugin Integration

  • Add agent-dev-memory-steward and update preflight, coordination, status, handoff, and improvement-review guidance.
  • Ask the mandatory PHI question and enforce synthetic-only development behavior for yes or unknown answers.
  • Add design-memory guidance and require frontend slices to submit visual evidence or a documented not-applicable disposition.
  • Package generic schemas and a provider-agnostic local bridge.
  • Keep BMAD as a control-plane adapter and project data out of reusable plugin files.

Phase 5 And 6: Proof And Handoff

  • Run focused tests, full tests, Ruff, mypy, docs checks, plugin validation, cache refresh, reinstall, and parity checks.
  • Use a fresh-context reviewer for provenance, concurrency, idempotence, supersession, context limits, PHI, secret handling, screenshot safety, and design-baseline integrity.
  • Freeze feature scope at minute 100 and begin handoff no later than minute 115.
