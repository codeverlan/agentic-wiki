Autonomous Long-Running Coordinator Build Plan

Build the executable coordinator that uses Agentic Wiki and the Agent Development Coordinator plugin to continue real software development until implementation and testing are complete.

Scope And Current Truth

Current truth: Agentic Wiki has a tested memory foundation, control-artifact renderers, authority and integrity controls, and reusable plugin policy. It does not yet have an executing scheduler, worker dispatcher, Git integrator, crash-recovery runner, or autonomous queue-draining process.

Execution rule: This is one dependency-driven queue. Workstream labels organize ownership; they do not create stopping points. The build continues across completed items, repairs, reviews, and newly discovered work until the completion predicate is proven.

Compatibility expansion: The completed release now has a separate flat extension plan for ChatGPT, Codex, public agents, and personalized private agents, including a worked plugin://seo-decision-lab@personal/ integration. Read Agent Compatibility Expansion; its machine-readable source is agent-compatibility-expansion.json.

Agentic Wiki
Owns the provider-neutral deterministic engine, journal, projections, scheduler, leases, recovery, completion evidence, and public API/CLI.
Plugin
Owns workflow policy, project adapter selection, host-specific workers and capabilities, preflight, supervision presentation, and immutable reusable contracts.
Project memory
Owns all project-specific intent, authority, queues, reports, incidents, external connections, design references, supervision requests, and evidence.
Workers
Write only slice-owned code, tests, fixtures, and reports. They never write shared control state or canonical memory.
Coordinator
Is the only shared-state and canonical-memory writer and integrates validated worker results serially.

Continuous Execution Loop

  1. Own
    Acquire or renew the fenced coordinator lease.
  2. Verify
    Validate the event journal and rebuild the projection.
  3. Reconcile
    Inspect workers, Git, receipts, resources, budgets, stops, and supervision.
  4. Recover
    Expire stale leases and preserve late or abandoned evidence.
  5. Derive
    Compute ready, waiting, blocked, terminal, and unreachable work.
  6. Discover
    Admit safe deduplicated proposals and enabling work.
  7. Contextualize
    Compile bounded memory and design context per assignment.
  8. Dispatch
    Start up to six nonconflicting workers.
  9. Validate
    Verify reports, ownership, tests, reviews, and capability evidence.
  10. Integrate
    Accept changes serially and rerun configured validation.
  11. Route blockers
    Record supervision needs while independent work continues.
  12. Project
    Update status, checkpoints, dashboards, and completion evidence.
  13. Replenish
    Add repairs, discoveries, missing proof, and unresolved obligations.
  14. Repeat
    Continue immediately until completion or a genuine whole-run boundary.

Stopping And Blocking Rules

A blocked item is not a stopped run. The coordinator must continue any implementation, testing, documentation, repair, review, recovery, integration, or enabling work that does not depend on the blocked decision.

  • User input becomes a blocker only after local evidence, official documentation, external research, installed capabilities, parallel review, slice splitting, and safe reversible alternatives have been exhausted.
  • A whole run may stop only for explicit user stop, a global safety/privacy/permission boundary, a configured hard usage boundary, proven completion, or a user-only blocker applying to every remaining item.
  • Transient resource failures use bounded retry and backoff. Exhaustion blocks the affected invocation or slice, not unrelated work.
  • User return and status requests do not cancel safe active work. At the next reasonable boundary, pending supervision becomes priority.
  • Queue drain is invalid while ready, active, stale, undisposed, outcome-unknown, or required dependent work exists.

Parallel Work Without Artificial Stops

  • As soon as AC-008 is validated, BMAD and lightweight adapters can run concurrently.
  • After the assignment contract exists, worker protocol, Git classification, validation execution, and capability discovery can progress on disjoint paths.
  • After reconciliation exists, recovery, supervision, observability, design evidence, and runner work proceed according to dependencies rather than a shared milestone.
  • Verification begins with each contract. Unit, property, fault, and integration tests are queue items, not a final testing period.
  • Every worker report may create repair or discovery work. Accepted additions become ordinary queue items and must be drained.

Verification Obligations

  • Unit and generated state-machine tests for every legal transition, dependency rule, lease operation, retry, blocker, authority decision, and completion condition.
  • Multiprocess concurrency and subprocess crash injection around every durable mutation and external receipt boundary.
  • Disposable Git repositories, local bare remotes, dirty trees, conflicts, divergent refs, push rejection, and crash-after-commit/push scenarios.
  • Scriptable workers for success, validation failure, hang, stale heartbeat, malformed report, forbidden edit, late result, and process death.
  • Fake MCP, API, plugin, browser, local-tool, credential, memory-runtime, and outage adapters with seeded deterministic schedules.
  • BMAD and lightweight end-to-end builds through real coordinator entry points.
  • Synthetic PHI yes/unknown projects with secret and PHI canaries across prompts, files, logs, screenshots, reports, Git, and HTML.
  • 8-24 hour soak runs with hundreds of slices, restarts, outages, randomized timing, resource-growth checks, and preserved failing seeds.
  • Independent reconstruction of final state from journal, projection, Git, validation receipts, and completion manifest.

Definition Of Complete

The autonomous coordinator build is complete only when all conditions below pass together:

  1. All 48 planned items and every accepted discovered item have validated terminal dispositions.
  2. No ready, active, stale, resolvable waiting, undisposed, uncertain, or required supervision work remains.
  3. All unit, property, concurrency, fault, Git, PHI, security, documentation, plugin, E2E, and soak gates pass.
  4. The event journal verifies and independently rebuilds the final projection.
  5. Local and configured remote Git evidence match the accepted integrated state.
  6. The immutable completion manifest reports and proves every condition individually.
  7. No secret/PHI canary, worker process, lease, lock, temporary worktree, or unbounded artifact remains.
  8. Plugin source/cache parity and fresh-context BMAD and lightweight smoke tests pass.
  9. Run-state, handoff, branch ledger, incident summary, dashboard snapshot, and control index point to the final evidence.
